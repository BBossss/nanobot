# HCIGuard 升级失败 / 升级后异常场景规格（V1）

## 1. 目的

本文档用于定义 HCIGuard 第一批重点打穿场景之一：升级失败 / 升级后异常。

目标是围绕当前已知的升级日志与升级服务，建立一条可落地的场景闭环，用于后续推进：

- 现有 Skill / policy 扩展
- inspection 规则
- case 沉淀结构
- 诊断工具调用顺序
- 结构化结论输出

---

## 2. 当前场景范围

V1 先聚焦于：

- 升级任务执行过程中失败
- 升级完成后出现异常
- 升级框架组件报错、卡住、异常退出

当前已明确可使用的排查入口如下。

### 2.1 日志入口

- 升级主日志：`/sf/log/today/update.log`
- 升级框架日志：
  - `/sf/log/today/upgrade-worker.log`
  - `/sf/log/today/upgrade-server.log`

### 2.2 相关服务

- `upgrade-server`
- `upgrade-worker`

---

## 3. V1 目标与非目标

### 3.1 V1 目标

V1 目标是做到：

1. 能围绕升级相关日志与服务快速采集关键证据
2. 能给出升级失败 / 升级后异常的初步分类
3. 能输出结构化结论与下一步建议
4. 能沉淀标准案例
5. 能为后续巡检与自动分析积累规则

### 3.2 非目标

V1 暂不追求：

- 覆盖所有升级异常分支
- 实现完整回滚编排
- 覆盖多节点升级时序重建
- 自动恢复升级流程
- 完整组件依赖拓扑推理

---

## 4. 典型现象分类

建议在 V1 中先按以下几类现象分类。

### 4.1 升级任务失败

现象示例：

- 升级任务直接失败
- 日志中出现明确 `error` / `failed` / `exception`
- 升级流程中断

### 4.2 升级任务卡住

现象示例：

- 长时间无进度
- worker / server 无明显退出但持续卡住
- 升级日志停留在固定阶段

### 4.3 升级后服务异常

现象示例：

- 升级完成但相关业务异常
- 升级服务仍有错误日志
- 服务状态异常、反复重启、未拉起

### 4.4 升级框架组件异常

现象示例：

- `upgrade-server` 未运行
- `upgrade-worker` 未运行
- 服务状态异常
- framework 日志出现异常栈或连接失败

---

## 5. 证据采集顺序

V1 建议的采集顺序如下：

### 第一步：确认现象和时间窗口

需要先确认：

- 用户感知到的故障现象
- 升级开始时间 / 异常出现时间
- 是“升级中失败”还是“升级后异常”

### 第二步：读取升级主日志

优先读取：

- `/sf/log/today/update.log`

重点关注：

- 最近时间窗口内的 `error`
- `failed`
- `exception`
- `timeout`
- 与升级阶段推进相关的关键行

### 第三步：读取框架日志

继续读取：

- `/sf/log/today/upgrade-worker.log`
- `/sf/log/today/upgrade-server.log`

重点关注：

- worker 执行失败
- server 调度失败
- 任务分发异常
- 连接、认证、超时、依赖失败

### 第四步：检查升级服务状态

服务：

- `upgrade-server`
- `upgrade-worker`

重点关注：

- 服务是否在运行
- 是否反复重启
- 是否未拉起
- 是否与日志时间线对应

### 第五步：汇总时间线

将以下信息对齐：

- 升级主日志阶段
- worker/server 关键错误
- 服务状态变化
- 用户观察到的异常时间点

---

## 6. 关键错误关键词（V1）

V1 建议优先关注以下关键词：

- `error`
- `failed`
- `failure`
- `exception`
- `panic`
- `timeout`
- `rollback`
- `retry`
- `refused`
- `unavailable`

后续应根据真实升级案例继续扩充专项关键词表。

---

## 7. 初步候选根因分类

V1 先不直接推根因，而是输出候选类型。

建议先按以下类别组织：

1. 升级框架自身异常
2. worker 执行失败
3. server 调度异常
4. 服务未正常拉起或异常退出
5. 外部依赖 / 连接 / 超时问题
6. 升级完成后遗留异常

要求：

- 结论必须区分“已证实”与“候选根因”
- 没有足够证据时，不允许把候选根因写成最终根因

---

## 8. 建议输出结构

针对升级失败 / 升级后异常，建议输出结构统一为：

1. 当前现象
2. 升级阶段判断
3. 已证实关键证据
4. 候选根因
5. 下一步建议
6. 风险说明

示例结构：

```text
现象：
升级过程中失败，当前升级未完成。

升级阶段判断：
从 update.log 看，流程卡在 xxx 阶段。

已证实关键证据：
- update.log 在 xx:xx:xx 出现 failed
- upgrade-worker.log 在 xx:xx:xx 出现 timeout
- upgrade-worker 服务状态异常

候选根因：
- worker 执行失败
- 外部依赖响应超时

下一步建议：
- 继续采样 worker/server 最近错误行
- 确认 upgrade-worker / upgrade-server 当前状态
- 结合时间线判断是否需人工介入

风险说明：
- 当前不建议直接重试或重启，需先确认失败阶段和遗留状态
```

---

## 9. 对 Case 沉淀的要求

该场景生成案例时，建议除基础字段外补充：

- `scenario = upgrade_failure`
- `impact_scope`
- `timeline`
- `root_cause_type`
- `actions_taken`

建议标签：

- `upgrade`
- `upgrade-failure`
- `upgrade-postcheck`

## 10. 与现有 Skill / policy 的关系

本场景优先通过扩展现有能力落地，而不是立即新增专项 Skill。

建议分工：

- `hci-troubleshooting`
  承载升级失败场景下的通用排障顺序、证据与结论表达
- `hci-case-summary`
  规范升级失败案例的总结结构
- `hci-inspection-analysis`
  在后续巡检化时承载升级异常报告口径
- policy / inspection 规则
  承载是否触发专项分析、是否转案例、是否做定时检查等规则

当前不建议：

- 为“升级失败”立即新增一个独立 Skill
- 在尚未沉淀足够真实案例前，把大量升级分支硬编码进 Skill

建议先做：

1. 用现有 Skill + 规则跑一段时间真实现场
2. 积累一批升级失败案例
3. 再决定是否有必要沉淀为独立专项能力
- `upgrade-failure`
- `upgrade-post-check`

这样可以为后续案例检索、专题案例库、导出与复盘分析提供更稳定的基础。

---

## 10. 对 inspection 的要求

当前该场景应为后续 inspection 能力预留以下规则方向：

- 升级日志中关键错误关键词扫描
- `upgrade-server` / `upgrade-worker` 服务状态检查
- 最近时间窗口内 upgrade 相关异常聚合

注意：

- 第一版 inspection 不应只做“定时 grep”
- 后续应增加：
  - 去重
  - 变化感知
  - 重复异常收敛

---

## 11. 对 Skill 的要求

该场景后续建议新增或增强专项 Skill，至少覆盖：

- 升级失败排障顺序
- 升级日志优先阅读顺序
- 常见候选根因分类
- 输出结构约束
- 风险提示模板

Skill 重点不在替代 diagnostics，而在于定义：

- 先查什么
- 再怎么看
- 如何组织结论

---

## 12. 下一步建议

围绕该场景，建议按以下顺序推进：

1. 先基于本文档补专项 Skill 初稿
2. 再补 inspection 规则
3. 再补 case 扩展字段
4. 最后再看是否需要新增专项 diagnostics 适配

这样可以先把场景闭环跑通，再决定是否继续下沉到更细的底层工具。
