# HCIGuard 高频 HCI 场景优先级清单（V1.5）

## 1. 目的

本文档用于在平台化 V2 路线下，优先选定 3 个最值得打穿的 HCI 高频场景，避免 HCIGuard 继续横向扩功能而失焦。

适用对象：

- 产品负责人
- 平台研发
- 排障规则维护人员
- 一线实施 / 运维人员

---

## 2. 选型原则

优先选择以下类型的场景：

- 一线出现频率高
- 对业务影响明显
- 有较稳定的证据采集路径
- 能形成结构化根因候选
- 适合沉淀为案例、巡检、SOP 三位一体能力

不优先选择：

- 只在极少数环境出现的稀有场景
- 过度依赖某个单一客户环境的定制问题
- 没有稳定证据链的纯经验型问题

---

## 3. 推荐优先级

### P1. 升级失败 / 升级后异常

推荐理由：

- 影响大
- 问题复杂度高
- 现场排查价值高
- 最容易体现平台能力与场景能力结合的价值

典型现象：

- 升级任务失败
- 升级后服务异常
- 节点状态不一致
- 升级链路中断或卡住

建议平台补强点：

- 升级任务相关日志源聚合
- 升级阶段时间线整理
- 升级失败根因候选模板
- 升级后异常的检查顺序与风险提示

建议输出：

- 升级阶段摘要
- 当前失败点
- 关键证据
- 候选根因
- 回退 / 继续处理建议

### P2. 存储空间 / 磁盘 / 分区异常

推荐理由：

- 高频
- 可观测性强
- 证据路径稳定
- 容易形成标准化诊断和报告模板

典型现象：

- 磁盘空间不足
- 分区满
- IO 高
- latency 升高
- volume / 副本异常

建议平台补强点：

- 存储类 diagnostics 组合视图
- 磁盘 / 分区 / volume 关联信息
- 常见根因分类
- 告警 / 巡检差异感知

建议输出：

- 当前空间或 IO 状态
- 影响范围
- 关键证据
- 候选根因
- 止血 / 清理 / 验证动作

### P3. 服务挂掉 / D 状态 / 进程异常

推荐理由：

- 频率高
- 与日常值班最贴近
- 适合快速形成“证据 -> 结论 -> 建议”闭环

典型现象：

- 服务未拉起
- 服务反复重启
- 进程 D 状态
- 僵死进程
- 负载异常升高

建议平台补强点：

- systemd / process / journal 联动诊断
- D 状态专项 SOP
- 进程异常时间线整理
- 相关服务依赖链检查

建议输出：

- 服务当前状态
- 关键日志与进程证据
- 候选根因
- 下一步处理建议

---

## 4. 第二梯队场景

这些场景也重要，但建议放在第一批 3 个场景打穿之后推进。

### 4.1 网络异常 / 丢包 / 规则膨胀

特点：

- 很重要
- 但定位路径容易因环境差异变复杂
- 更适合在平台边界进一步稳定后推进

### 4.2 容器运行时 / 挂载泄漏 / 文件残留

特点：

- 对平台价值高
- 但证据来源和环境差异较大
- 更适合作为第二批专项场景

### 4.3 节点健康异常 / 资源倾斜 / 负载不均

特点：

- 场景常见
- 但容易和存储、服务、网络问题交叉
- 适合在前 3 个场景收口后再专项深化

---

## 5. 每个场景建议打穿的能力清单

每个入选场景，建议至少打通以下 7 个能力点：

1. 现象分类
2. 关键日志源
3. 关键状态采样
4. 候选根因模板
5. 标准输出结构
6. case 沉淀模板
7. inspection / 巡检可复用规则

换句话说，目标不是只补一个 Skill，而是形成：

- diagnostics
- case
- inspection
- skill
- policy

的一体化场景能力。

---

## 6. 推荐推进顺序

建议顺序如下：

1. 升级失败 / 升级后异常
2. 存储空间 / 磁盘 / 分区异常
3. 服务挂掉 / D 状态 / 进程异常

原因：

- 第一项最能体现平台复杂场景价值
- 第二项最容易形成稳定可复用 SOP
- 第三项最贴近日常值班和高频使用

---

## 7. 最终建议

当前 HCIGuard 最值得做的，不是继续扩展更多零散工具，而是围绕以上 3 个场景形成稳定战斗力。

只要前 3 个场景能做到：

- 自动采集证据
- 归纳候选根因
- 输出结构化结论
- 生成 case 与巡检规则

HCIGuard 就会从“排障平台雏形”进入“具备明显实战价值的平台”阶段。
