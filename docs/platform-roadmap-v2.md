# HCIGuard 平台化 V2 路线

## 1. 目的

本文档用于把当前 HCIGuard 从 “已具备排障闭环的 V1 雏形” 进一步推进为 “可长期演进的排障平台”，明确：

- 当前平台已经具备哪些基础
- 下一阶段最值得投入的任务
- 哪些任务优先级最高
- 平台化目标下，哪些事情不应继续优先投入

适用对象：

- 产品负责人
- 技术负责人
- 平台开发人员
- 运维与实施负责人

---

## 2. 当前判断

HCIGuard 当前已经不再是“给 nanobot 换个皮”的轻度改造，而是一个面向 HCI 场景的排障平台雏形。

当前已具备的平台基础包括：

- 只读诊断工具
- 巡检与报告
- 案例沉淀、导入、检索
- 执行审批与审计
- CLI / Telegram / Mattermost 多入口
- Skill / policy / 主代码三层分离的初步结构

当前最需要解决的问题，不是继续横向堆工具，而是让平台在高频场景上形成稳定战斗力。

---

## 3. V2 核心目标

V2 建议围绕以下目标推进：

1. 把 HCIGuard 从“通用排障底座”推进为“高频 HCI 场景可打穿的平台”
2. 继续强化案例、巡检、审计、审批这些平台能力
3. 让 Skill / policy / domain code / runtime code 的边界进一步收口
4. 为跨主机、多数据源、多系统集成预留结构化扩展口

---

## 4. 下一阶段最该做的 5 个任务

### 4.1 打穿 3 个高频 HCI 场景

这是 V2 最值得优先投入的任务。

目标不是继续泛化扩工具，而是挑选 3 个高频场景，形成从证据采集到结论输出的完整能力。

建议优先候选：

- 升级失败 / 升级后异常
- 存储空间 / 磁盘 / 分区异常
- 服务挂掉 / D 状态 / 进程异常
- 网络异常 / 丢包 / 规则膨胀
- 容器运行时 / 挂载泄漏 / 文件残留

每个场景建议打通：

- 证据采集路径
- 关键日志源
- 候选根因模板
- 结论结构
- 下一步建议
- 案例沉淀格式

成功标志：

- 对同类场景的输出稳定
- 不再只是“帮你 grep”
- 能形成“像现场工程师在排”的行为风格

### 4.2 增强案例数据模型

当前案例已经结构化，但仍不足以支撑长期平台复用。

建议补充的重点字段：

- `impact_scope`
- `timeline`
- `root_cause_type`
- `actions_taken`
- `automation_candidate`

目标：

- 避免案例库长期演化成“可搜但难复用的文本堆”
- 为后续导出、分析、专题案例库建设提供更强支撑

### 4.3 把 inspection 升级为变化感知巡检

当前 inspection 已经具备扫描、分析、报告、转案例链路，但下一步重点不该是继续增加扫描项，而应该是：

- 同类异常去重
- 重复问题收敛
- 基于上次结果做 diff
- 明确异常等级

目标：

- 避免 inspection 退化为“定时 grep 机器人”
- 提升报告的可读性和行动价值

### 4.4 把 IM 从聊天入口升级为协同入口

当前 Telegram / Mattermost 已可作为交互入口，但仍偏“会聊天”。

下一步建议优先补：

- case id 回链
- report path 回链
- 执行结果与案例/报告关联
- 线程内上下文增强
- 升级 / 交接 / 跟踪友好的结构化输出

目标：

- 让 IM 不只是“远程终端”
- 而是“会留痕、会回链、会协同”的平台入口

### 4.5 正式收口平台三层结构

建议将后续代码组织逐步收口为三层：

#### Runtime Layer

负责：

- agent loop
- message bus
- session
- provider
- channels
- cron / heartbeat

#### HCI Domain Layer

负责：

- diagnostics adapters
- inspection policies
- case schema
- HCI skills
- 专项 SOP
- 命令白名单与 HCI 规则

#### Delivery / Ops Layer

负责：

- CLI
- Telegram / Mattermost
- report output
- 审计输出
- 部署方式

目标：

- 减少平台长期维护压力
- 降低上游 runtime 演进对 HCI 定制层的冲击

---

## 5. 哪些事情当前不应继续优先投入

在 V2 路线中，现阶段不建议优先做：

- 继续新增更多 IM 渠道
- 继续扩张更多零散工具
- 过早建设完整 Web UI
- 在没有场景闭环前继续堆更多 prompt/skill 数量

原因：

- 当前瓶颈不在入口数量
- 当前瓶颈不在工具数量
- 当前平台最缺的是高频场景打穿与平台边界收口

---

## 6. 建议的推进顺序

建议按如下顺序推进：

1. 先确定 3 个高频 HCI 场景
2. 同步增强案例模型
3. 升级 inspection 的变化感知能力
4. 强化 IM 协同入口能力
5. 在此过程中持续收口三层架构

---

## 7. 最终判断

HCIGuard 后续最强的路线，不是做成“大而散的运维百宝箱”，而是做成：

- 有平台底座
- 有安全边界
- 有案例资产
- 有巡检闭环
- 能打穿几个高频 HCI 场景

一旦这几条线打通，HCIGuard 就会从“排障代理雏形”进入“可交付的排障平台”阶段。
