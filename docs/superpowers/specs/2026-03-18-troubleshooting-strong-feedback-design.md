# 排障强反馈设计

## 1. 目标

本文档定义 HCIGuard 下一阶段在交互式排障中的“强反馈”设计。

本阶段目标不是改造排障结论能力，而是让用户在调查过程中始终知道：

- 当前进行到哪个阶段
- 系统为什么要查这一步
- 长耗时期间系统没有卡住
- 最终结论前，系统刚才大致做了什么

首版目标：

- 默认在排障过程中持续输出短反馈
- 关键调查动作前输出一句“为什么查这一步”
- 长耗时期间提供心跳反馈
- 最终结论前追加简短过程摘要
- 反馈格式可程序化生成，不依赖 LLM 临场发挥

本阶段不做：

- 独立 Web 进度面板
- 复杂可视化时间线
- 基于任意工具的自由解释性长文
- 对所有历史消息做完整过程回放

## 2. 产品行为

### 2.1 默认反馈位置

首版采用“两层反馈”：

- 过程里持续短播报
- 最终结论前再输出一段简短过程摘要

也就是说，反馈既存在于过程流里，也在最终阶段做一次高度压缩回顾。

### 2.2 用户感知目标

用户在整个排障过程中至少应感知到：

- 现在是在“识别目标/范围”还是“执行只读检查”
- 这一步是因为上一条证据、当前假设或当前范围判断而触发
- 如果正在等待，系统仍在工作，而不是沉默卡住
- 最终结论前，系统能够回顾刚才的关键调查路径

## 3. 反馈事件模型

首版引入一层结构化反馈事件，而不是把解释完全交给 LLM。

### 3.1 `stage`

表示当前处于哪个阶段。

首版建议固定阶段：

- `初始化上下文`
- `识别目标/范围`
- `生成调查计划`
- `执行只读检查`
- `汇总证据`
- `输出判断`

### 3.2 `reason`

表示为什么要执行当前关键调查动作。

要求：

- 必须与当前证据、当前假设或刚发生的范围切换挂钩
- 必须是中等粒度
- 不能只是泛化描述，例如“为了排障”

推荐格式：

- `刚才日志里出现 timeout，所以先检查服务状态，判断是服务本身异常还是下游依赖异常。`

### 3.3 `action`

表示正在执行什么具体调查动作。

例如：

- `正在检查服务状态：service_status(nginx)`
- `正在读取日志：read_log_tail(/var/log/app.log)`

### 3.4 `heartbeat`

表示当前仍在执行同一阶段，避免长时间沉默。

要求：

- 简短
- 不重复长解释
- 若是多节点场景，可带简单进度

例如：

- `仍在读取日志，请稍等。`
- `仍在汇总多节点结果，已完成 2/5。`

### 3.5 `summary`

表示最终输出前的简短过程摘要。

要求：

- 只回顾关键调查路径
- 不重复最终结论全文
- 不展开冗长推理

例如：

- `刚才先检查了日志和服务状态，再对比了多节点结果；当前更像共享依赖异常，不像单点服务挂掉。`

## 4. 触发规则

### 4.1 必须发 `reason`

以下时机必须生成 `reason`：

- 第一次进入调查阶段时
- 每次切换调查方向时
- 从日志调查切到服务/进程/磁盘/网络等不同证据源时
- 从单节点扩展到多节点时

### 4.2 只发 `stage`

以下时机只需要 `stage`：

- 普通阶段切换
- 同一调查方向内继续执行相似动作
- 不需要解释调查意图变化的连续只读动作

### 4.3 发 `heartbeat`

以下时机必须发 `heartbeat`：

- 单次等待超过阈值时
- 多节点 fan-out 期间存在明显等待时
- 日志搜索、日志读取、聚合汇总这类用户感知上容易误以为“卡住”的动作时

首版建议阈值：

- 超过 `3 秒` 发第一次 heartbeat
- 之后每 `5 秒` 再发一次，直到当前阶段结束

## 5. 文案风格

### 5.1 总体风格

首版反馈文案应像一个现场工程师边查边解释，而不是：

- 系统日志
- 空泛安慰
- 过度解释的教程

### 5.2 `stage` 风格

要求：

- 很短
- 明确当前阶段

例如：

- `正在识别目标范围。`
- `正在执行只读检查。`

### 5.3 `reason` 风格

要求：

- 使用“证据 -> 目的”的结构
- 必须和上一条证据或当前假设有关

例如：

- `刚才日志里出现 timeout，所以先检查服务状态，判断是服务异常还是下游依赖异常。`

### 5.4 `heartbeat` 风格

要求：

- 只报状态
- 不重复完整原因

例如：

- `仍在读取日志，请稍等。`
- `仍在汇总多节点结果，已完成 2/5。`

### 5.5 `summary` 风格

要求：

- 很短
- 聚焦关键路径

例如：

- `刚才先检查了日志和服务状态，再对比了多节点结果；当前更像共享依赖异常。`

## 6. 总体架构

首版建议在 agent loop 内增加一个轻量反馈层，而不是新建复杂运行时子系统。

### 6.1 Feedback Emitter

该组件负责在 agent 执行过程中生成结构化反馈事件。

输入：

- 当前阶段
- 当前工具调用
- 最近一条调查原因
- 是否进入多节点模式
- 是否处于长耗时等待

输出：

- `stage`
- `reason`
- `action`
- `heartbeat`
- `summary`

### 6.2 Feedback Formatter

该组件负责把结构化反馈事件渲染成用户可见文本。

首版要求：

- 输出稳定
- 文案短
- 不依赖 LLM

### 6.3 Transport Reuse

当前已有 progress callback / bus 机制应继续复用。

首版不新增独立 transport 层，只在现有 progress 通路中补充更明确的反馈内容。

## 7. 数据流

### 7.1 单节点场景

1. 用户发起排障请求
2. 系统输出 `初始化上下文`
3. 系统输出 `识别目标/范围`
4. 若进入调查动作，先输出 `生成调查计划`
5. 执行关键动作前输出 `reason`
6. 执行中输出 `action`
7. 若等待过久，输出 `heartbeat`
8. 聚合后输出 `汇总证据`
9. 结论前输出 `summary`
10. 再输出最终判断

### 7.2 多节点场景

在单节点流程基础上增加：

- 范围确认后的多节点阶段说明
- fan-out 过程中的进度心跳
- 汇总阶段的多节点进度提示

## 8. 错误处理

### 8.1 无法解释当前调查动作

若系统无法稳定生成与证据挂钩的 `reason`：

- 不要硬编解释
- 至少保留 `stage` 和 `action`

### 8.2 长耗时但无可见进度

若当前无法获得精确进度：

- 仍需输出通用 heartbeat
- 明确说明“仍在执行”而不是保持沉默

### 8.3 最终输出过长

若最终结论已经很长：

- `summary` 仍然保留
- 但必须压缩到 1 到 2 句

## 9. 测试策略

### 9.1 阶段反馈测试

覆盖：

- 单节点调查过程中出现稳定阶段反馈
- 阶段顺序不混乱

### 9.2 原因说明测试

覆盖：

- 关键调查动作前有 `reason`
- 不同证据源切换时能触发新的 `reason`

### 9.3 心跳反馈测试

覆盖：

- 长耗时动作会触发 heartbeat
- 多节点场景可以输出简短进度

### 9.4 过程摘要测试

覆盖：

- 最终结论前存在简短过程摘要
- 摘要不会变成冗长重复结论

## 10. 验收标准

本阶段完成的最低标准：

- 用户在排障过程中始终能看到当前阶段
- 关键调查动作前能看到“为什么查这一步”
- 长耗时期间不会长时间静默
- 最终结论前有简短过程摘要

## 11. 后续演进

后续可继续扩展但不在本阶段实现：

- 为 IM 渠道做更细的反馈裁剪
- 为不同场景提供不同 `reason` 模板
- 提供可折叠的过程日志/过程回放
- 提供更强的多节点执行进度可视化
