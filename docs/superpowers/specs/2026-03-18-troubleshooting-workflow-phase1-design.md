# 排障工作流 Phase 1 设计

## 1. 目标

`Troubleshooting Workflow Phase 1` 的目标不是让 agent 更会说，而是让调查过程具备最基本的可审阅、可打断、可改方向、可缩范围的交互式控制能力。

本阶段优先解决的问题是：

- 用户可以在排障过程中打断当前调查
- 用户可以调整调查方向
- 用户可以缩小调查范围
- 这些控制会被系统显式收口为会话状态，而不是依赖模型临时记忆

## 2. 核心原则

- 本项目的第一目标仍然是强大的排障能力
- 控制只能约束调查，不替代调查判断
- 控制层是粗粒度约束，不是细粒度编排
- 已获取证据应保留，不因控制而被清空
- 不得绕过现有只读、审批、审计和范围确认边界

## 3. 范围

### 3.1 Phase 1 支持的能力

- 暂停当前调查推进
- 从当前上下文继续调查
- 改变优先调查方向
- 缩小调查范围
- 用自然语言和固定短指令两种方式表达控制意图

### 3.2 Phase 1 不做的事情

- 不做完整 workflow engine
- 不做复杂多分支计划编辑
- 不支持用户逐步编排完整调查脚本
- 不做自动修复编排
- 不做集群级任务调度系统

## 4. 控制模型

### 4.1 外部交互

控制输入采用双轨：

- 自然语言
  - `先别扩到多节点`
  - `只查日志`
  - `先不要看服务状态`
- 固定短指令
  - `暂停`
  - `继续`
  - `只查日志`
  - `不要多节点`

### 4.2 内部控制意图

外部输入统一映射成少量控制意图：

- `pause`
- `resume`
- `change_focus`
- `narrow_scope`

这些意图都只约束“接下来怎么调查”，不允许用户接管完整调查编排。

## 5. 会话状态设计

Phase 1 不引入新的 workflow engine，先挂在现有会话状态和 `AgentLoop` 周边。

建议新增最少状态：

- `paused: bool`
- `focus_hint: str | None`
- `scope_constraints`
- `last_control_reason: str | None`

约束如下：

- `pause`：停止继续发起新的调查动作
- `resume`：从当前上下文继续
- `change_focus`：调整后续调查优先级，但不清空已有证据
- `narrow_scope`：对后续工具调用施加范围约束，不能悄悄重新扩到多节点

## 6. 用户体验

控制反馈应像“驾驶舱确认”，而不是长篇聊天解释。

### 6.1 控制确认

示例：

- `已暂停当前排查；如需继续，请回复“继续”。`
- `后续先按日志方向继续调查。`
- `后续保持单节点模式，不扩到多节点。`

### 6.2 控制生效说明

示例：

- `已缩小范围到 node-a；后续调查会优先基于该节点。`
- `已调整方向；接下来先检查日志，再决定是否需要查服务状态。`

### 6.3 控制后的调查衔接

示例：

- `当前已拿到的证据会保留，下面按新的范围继续调查。`
- `当前先不扩查多节点；如果证据不足，我会先说明原因再请求你确认。`

## 7. 测试边界

Phase 1 至少需要覆盖以下行为：

- 普通聊天不会被误识别为控制命令
- `pause` 后不会继续推进新的调查动作
- `resume` 后能基于现有上下文继续
- `change_focus` 会影响后续调查优先级
- `narrow_scope` 会约束后续工具调用范围
- 多节点被禁止后不会悄悄重新扩查

## 8. 非目标

本阶段明确不做：

- 可视化流程编辑器
- 任意调查步骤的插入、删除、重排
- 复杂并行调查分支
- 自动修复工作流
- 泛化的跨主机编排平台

## 9. 推荐结论

Phase 1 推荐采用“双轨输入、统一控制意图、粗粒度约束”的方案。

即：

- 外部同时支持自然语言和固定短指令
- 内部统一收敛为少量控制意图
- 控制只改变调查边界和优先级，不替代 agent 的调查判断

这样可以在不削弱排障能力的前提下，为后续交互式调查控制打下稳定基础。
