# README 排障强反馈动图设计

## 1. 目标

在 `README.md` 中补充一个简短的终端动图，直观展示 HCIGuard 在排障过程中的“强反馈”体验。

本次动图不追求完整排障闭环，只强调最近已落地的用户可感知能力：

- 阶段反馈
- 调查原因提示
- 工具动作提示
- 长耗时 heartbeat
- 最终结论前的过程摘要

## 2. 设计原则

- README 优先：动图应能在 GitHub 页面中一眼看懂，不依赖额外说明。
- 短而清晰：总时长控制在约 8 到 12 秒。
- 终端真实感：整体视觉保持 CLI 风格，而不是海报式宣传图。
- 内容受控：直接使用固定脚本展示，不从真实 LLM 调用或在线环境录屏生成。

## 3. 展示内容

建议展示一个单节点排障片段，用户输入如下：

```text
检查 /var/log/app.log 最近 200 行是否有 timeout，并给出结论
```

动图中的关键输出顺序如下：

1. `初始化上下文`
2. `识别目标/范围`
3. `生成调查计划`
4. `为了先确认最近的异常线索，所以先读取日志，判断问题更像报错、超时还是依赖异常。`
5. `正在读取日志：read_log_tail(/var/log/app.log)`
6. `仍在读取日志，请稍等。`
7. `汇总证据`
8. `刚才先检查了日志；下面给出当前判断。`
9. `输出判断`
10. `结论：最近日志里能看到 timeout，当前更像请求超时或下游依赖响应慢，暂未看到服务退出迹象。`

## 4. 落地方式

首版采用“程序化生成 GIF”而不是录屏工具链，原因如下：

- 仓库内暂无现成录屏脚本或 GIF 生成流程
- 当前环境仅确认存在 `ffmpeg`
- 程序化生成更稳定，可重复构建，适合 README 资产

建议新增一个轻量脚本，在仓库内直接生成：

- 输出路径：`assets/demo/troubleshooting-strong-feedback.gif`
- 生成脚本：`scripts/render_troubleshooting_demo_gif.py`

## 5. README 放置位置

动图放在 `README.md` 的 `End-to-End Troubleshooting Example` 之前或该节内部靠前位置。

推荐结构：

1. 一句简短引导文案
2. GIF
3. 再接文字版排障示例

这样用户先看到交互体验，再看细节说明。

## 6. 非目标

本次不做以下内容：

- 不展示多节点确认/执行流程
- 不构建完整的录屏工具链
- 不新增 README 视频托管方案
- 不把动图扩展成完整产品宣传素材库
