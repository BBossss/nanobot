# HCIGuard Shell-First / SSH-First 排障 Agent 设计

## 1. 目标

本文档定义 HCIGuard 下一阶段的主设计方向：把它从偏保守的排障助手，推进为一个面向内部工程师、以排障能力优先的 shell-first / ssh-first 排障 agent。

本设计面向的使用环境是：

- 内部工程师
- 测试 / 预发 / 内网排障机
- 单次以单台目标机排障为主
- 希望覆盖大多数场景，并达到中等可用
- 第一优先级是让 agent 能持续调查，而不是先做重型安全治理

本阶段只保留最小必要边界：

- 不执行明显破坏性动作
- SSH 密码不落盘
- SSH 密码不进入普通会话历史、case、memory 或审计正文

## 2. 产品方向

HCIGuard VNext 应该优先变成：

- 一个 shell-first 的排障 agent
- 一个 ssh-first 的排障 agent
- 一个广覆盖的只读调查系统
- 一个能连续调查，而不是查一两步就停住的 agent

本阶段不应优先把它做成：

- 面向生产环境的强保守最小权限平台
- 通用远程运维平台
- 只擅长少数场景的强硬编码排障机器人

期望交互链路是：

1. 用户描述问题和目标主机
2. agent 自主采集本机或远程主机的只读证据
3. agent 根据当前证据继续调查 2-4 轮
4. agent 收窄问题范围，并输出结构化结论与下一步建议

## 3. 成功标准

第一版实现完成后，系统在大多数常见单机排障场景中应至少做到：

- 接收目标主机并建立 SSH 连接
- 本地或远程执行较自由的只读命令
- 在用户没有提供精确路径时，自己找到较可能的日志和状态入口
- 自主完成 2-4 轮调查
- 因“缺少手脚”而卡死的情况明显减少
- 即使不能完全确认根因，也能把问题明显收窄

本阶段明确不做：

- 多主机编排
- 重型凭据治理系统
- inspection diff / 变化感知巡检
- 大规模 case 模型重构
- 复杂审批框架

## 4. 总体架构

本设计保留当前 `AgentLoop` 作为中枢，但在其周边增加 3 个清晰分层。

### 4.1 Target / Session 层

这一层负责描述“排障动作在哪执行”。

核心概念：

- `Target`
  - `id`
  - `kind`：`local` 或 `ssh`
  - `host`
  - `port`
  - `username`
- `TargetSession`
  - 针对某个目标机的会话上下文
  - 可以持有当前进程内存中的 SSH 密码状态

职责：

- 表示当前排障目标
- 区分本机与远程执行
- 为一次排障过程提供稳定的执行目标

### 4.2 Executor 层

这一层负责“如何执行”。

职责：

- 在指定目标上执行只读 shell 命令
- 为远程目标处理 SSH 传输
- 在当前进程内处理密码型 SSH
- 统一 stdout / stderr / exit code / timeout / target 元数据
- 处理最小必要的破坏性命令边界
- 输出脱敏后的审计信息

这一层不负责排障语义，不回答“服务 X 该看什么日志”。

### 4.3 Troubleshooting Actions 层

这一层负责“排障要查什么”。

典型动作：

- `find_logs`
- `read_log_tail`
- `search_log`
- `service_status`
- `process_snapshot`
- `disk_snapshot`
- `network_snapshot`
- `journal_tail`
- `find_recent_files`
- `expand_by_keyword`
- `expand_by_service`

这些动作都接收 `target`，但不关心底下是本机执行还是 SSH 执行。

### 4.4 Skills 层

Skill 继续负责：

- 排障流程约束
- 服务与日志映射
- 扩查规则
- 输出结构
- 环境知识

Skill 不替代实际执行能力，它只指导 agent 如何使用工具和 shell 能力。

## 5. 为什么不能只靠 exec

`exec` 必须保留，而且在第一版里必须变强，因为这是最快提升排障能力的路径。

但系统不能长期只依赖自由 `exec`，原因是：

- 行为稳定性差
- 输出难以规范化
- 高频排障路径难以产品化
- 后续 case / inspection / 场景增强难以沉淀

因此本设计采用混合模式：

- 主路径：调查动作 + shell-first 调查
- 兜底路径：更自由的 `exec`

这不是“工具优先、完全不用 shell”，也不是“全都靠自由 shell”。

## 6. 执行模型

### 6.1 Shell-First / SSH-First

第一版应把当前 `exec` 升级成排障执行底座。

要求：

- 支持 `target=local`
- 支持 `target=<remote host>`
- 当目标为远程主机时，自动通过 SSH 执行
- 保留当前输出风格，但补强 target 感知和排障可用性

### 6.2 最小必要边界

本阶段不先做重型安全系统，但仍要继续禁止明显变更行为：

- 文件写入与编辑
- 服务重启 / 停止 / reload
- `kill`、`pkill`、`killall`
- 任何写入型 shell 重定向
- 明显危险的管理员命令
- 交互式 shell / 长时间阻塞式命令

实用原则是：

- 尽量放开只读调查
- 明确禁止变更动作

### 6.3 密码型 SSH

密码型 SSH 是必须能力。

第一版约束如下：

- CLI 和 IM 都支持
- 密码只存在当前进程内存里
- 密码不写入 session history、case、memory 文件、审计正文
- 本阶段不做超时 / lease 子系统
- 本阶段不加显式清理密码命令
- 密码随进程结束而消失

这是一个明显偏提效、而不是偏强治理的取舍。

## 7. Agent 调查模型

当前最关键的问题不是模型不会回答，而是缺少足够的下一步动作，所以经常停在半路。

本设计的重点不是先把模型做“更聪明”，而是让 `AgentLoop` 支持连续调查。

### 7.1 理想调查流程

对一条普通排障请求，默认流程应是：

1. 确认目标主机和现象
2. 找候选证据入口
3. 做第一轮有界采样
4. 基于证据再扩查 1-3 轮
5. 当没有明显下一步只读动作时收敛输出

### 7.2 AgentLoop 需要补的能力

`AgentLoop` 应增加轻量调查支持：

- 会话中的目标机感知
- 短生命周期的调查上下文缓存
- 重复动作抑制
- 无新增证据时的收敛规则

调查缓存至少要记住：

- 已采样过哪些日志
- 已检查过哪些服务
- 已扩查过哪些关键词
- 哪些方向已经失败
- 哪些证据片段值得继续追踪

这一层必须保持轻量，不在本阶段引入重型 planner 子系统。

### 7.3 收敛规则

最低限度应做到：

- 不要对同一对象用同样参数反复采样
- 没有新证据时，不要反复看同一服务
- 连续两轮无新增证据时应收敛
- 缺少核心信息时，要明确追问，而不是盲查

## 8. 第一阶段能力建设

本阶段优先目标是“广覆盖中等可用”，不是“少数场景特别强”。

### 8.1 P0 能力

必须优先补上：

- 支持 target 的增强版 `exec`
- 基于 SSH 的远程执行
- `find_logs`
- `read_log_tail`
- `search_log`
- `service_status`
- `process_snapshot`

这组能力首先解决“agent 没有下一步可做”的问题。

### 8.2 P1 能力

第二优先级补上：

- `journal_tail`
- `disk_snapshot`
- `network_snapshot`
- `find_recent_files`
- `expand_by_keyword`
- `expand_by_service`

这组能力决定 agent 能不能明显提升“会继续查”的体感。

### 8.3 P2 能力

等主调查链路跑顺后再做：

- 时间线收集
- 异常前后窗口对比
- 更强的证据摘要
- 少量高频场景增强

## 9. Skill 与 Tool 的边界

### 9.1 适合做成 Skill 的

- 通用排障流程
- 服务 / 日志映射
- 场景 SOP
- 关键词扩查策略
- 证据组织规则
- 输出结构
- 环境知识

### 9.2 适合做成 Tool 的

- 本机 / 远程执行能力
- 读日志
- 搜日志
- 找日志
- 服务 / 进程 / 磁盘 / 网络状态采集
- journal 读取
- 需要真实执行的扩查动作

### 9.3 组合原则

正确分工是：

- Skill 教 agent 怎么查
- Tool 给 agent 真正的手脚

不能指望 Skill 单独弥补执行能力不足。

## 10. 实施顺序

### 10.1 Phase 1

重点：

- 引入 target 抽象
- 把 `exec` 升级成 target-aware 执行底座
- 补远程 SSH 执行
- 用最小代价支持密码型 SSH
- 补最小可用调查动作集

结果：

- agent 对单台本机或远程主机的排障死角明显减少

### 10.2 Phase 2

重点：

- 调查上下文缓存
- 扩查动作
- 重复动作抑制
- 多轮调查连续性

结果：

- agent 能明显更连续地推进调查，而不是每轮都像重新开始

### 10.3 Phase 3

重点：

- 输出质量优化
- 环境适应能力增强
- 高频场景加速包

结果：

- 对重复问题族的表现更稳定

## 11. 错误处理

第一版必须明确处理：

- SSH 连接失败
- SSH 认证失败
- 远程无权限
- 主机不可达
- 命令超时
- 日志不存在
- 搜索结果为空
- 输出过大或无效

这些错误应以结构化方式返回，便于 agent 判断：

- 是否换一种查法
- 是否切换证据入口
- 是否需要向用户补问信息
- 是否该停止并总结当前限制

## 12. 测试策略

本阶段测试重点应放在“排障行为是否变强”，而不是先做完整安全模型回归。

最低覆盖应包括：

- 本机 / 远程 target-aware `exec`
- SSH 密码不进入 session 持久化路径
- SSH 基础失败场景
- 调查动作对 executor 返回值的处理
- 重复调查抑制逻辑
- 单机排障的代表性端到端链路

测试不只看输出是否正确，还要看调查链是否真的能继续：

- 能不能迈出第一步
- 能不能迈出有价值的第二步
- 会不会明显重复或空转

## 13. 风险与取舍

这个设计是明确偏向排障能力的。

已知取舍包括：

- 密码暂驻进程内存，简化实现
- 更自由的 shell 调查会增加行为波动
- 广覆盖只读调查会带来更多噪声
- 第一版更擅长“收窄问题”，未必总能给出高置信根因

对当前目标环境，这些取舍是可接受的：

- 内部工程师
- 测试 / 预发 / 内网排障机

对生产级广泛部署，这套取舍则不够。

## 14. 最终建议

HCIGuard VNext 应按以下原则推进：

- shell-first
- ssh-first
- target-aware
- 广覆盖只读调查优先
- 调查动作 + 自由 `exec` 兜底

第一阶段不要让项目依赖于：

- 重型安全架构
- 完整凭据平台
- 大量刚性场景工具

最快产生用户体感价值的路径是：

1. 让 `exec` 支持 target 和 SSH
2. 补一小组高价值调查动作
3. 让 `AgentLoop` 能继续调查，而不是早停
