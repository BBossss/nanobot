# Root Cause Candidates 设计

## 1. 目标

本文档定义 HCIGuard 下一阶段的“候选根因”能力设计。

本阶段目标不是自动确认根因，也不是引入复杂规则库，而是在当前排障会话已经拿到的证据基础上，生成受约束的候选根因摘要。

首版目标：

- 只基于当前会话已采集证据
- 程序先做轻量信号提取和候选归类
- LLM 只负责整理输出，不允许发明新候选类型
- 输出必须明确是“候选根因”，不得写成“已确认根因”
- 每个候选都必须附支持证据

本阶段不做：

- 历史 case 参考
- 外部规则库文件
- 置信度评分
- 验证动作模板
- 自动写回 case 元数据

## 2. 输入范围

首版只接收当前这轮调查已经拿到的证据，不额外主动采集。

允许使用的输入包括：

- 多节点共性异常摘要
- 多节点局部异常摘要
- 日志时间线
- 原始日志片段

不允许使用：

- 历史 case
- inspection 历史报告
- 外部知识库

## 3. 产品行为

### 3.1 默认行为

若当前证据不足以形成稳定候选，则不输出候选根因。

应明确输出：

- 当前证据不足以形成候选根因

### 3.2 输出边界

首版输出只回答两个问题：

- 当前证据最像哪类问题
- 哪些已观测证据支撑这个候选

不回答：

- 是否已经确认根因
- 置信度多高
- 应该如何修复

## 4. 总体架构

首版建议新增独立的 `root_cause_candidates` 模块，作为多节点摘要和时间线之后的一层后处理。

### 4.1 Signal Extraction

该组件负责把当前证据提炼为有限信号。

输入：

- 多节点摘要
- timeline 摘要
- 原始日志片段

输出：

- 信号列表 `signals`

首版信号示例：

- `timeout`
- `connection_refused`
- `unreachable`
- `retry_exhausted`
- `service_exit`
- `service_crash`
- `single_node_only`
- `cross_node_common`
- `dependency_backend`

### 4.2 Candidate Mapping

该组件负责把有限信号映射到有限候选类型。

输入：

- 提取出的信号
- 支撑这些信号的证据引用

输出：

- 候选根因列表

每个候选至少包含：

- `candidate_type`
- `evidence_refs`

### 4.3 LLM Formatting Layer

LLM 仅负责把程序已生成的候选和证据整理成自然语言输出。

约束：

- 不允许发明新候选类型
- 不允许把候选写成已确认根因
- 不允许没有证据时输出候选

## 5. 候选类型边界

首版候选类型建议限制在 5 类以内。

### 5.1 跨节点共享连接/超时异常

适用于：

- 多个节点在接近时间出现 `timeout` / `refused` / `unreachable`

### 5.2 局部节点异常

适用于：

- 异常集中在单个节点或极少数节点
- 没有形成明显跨节点共性

### 5.3 服务执行失败/异常退出

适用于：

- 日志中出现 `failed` / `exit` / `crash` / `panic`

### 5.4 重试耗尽/任务卡住

适用于：

- 出现 `retry` / `retried` / `exceeded` / `stuck`

### 5.5 依赖不可达或下游异常

适用于：

- 日志明确指向 backend / upstream / dependency / storage backend

## 6. 输出结构

首版输出固定为两段。

### 6.1 Candidate Root Cause

最多输出 1 到 2 个候选项。

示例：

```text
Candidate Root Cause
- 候选根因：跨节点共享连接/超时异常
- 候选根因：依赖不可达或下游异常
```

### 6.2 Supporting Evidence

每个候选下必须附 2 到 4 条支持证据。

证据来源只能是：

- 共性异常摘要
- 局部异常摘要
- timeline 关键事件
- 原始日志片段

## 7. 错误处理

### 7.1 证据不足

若无法提取足够信号：

- 不输出候选根因
- 输出“当前证据不足以形成候选根因”

### 7.2 候选冲突

若多个候选都能命中，但互相冲突：

- 最多保留 2 个
- 必须都标记为候选

### 7.3 弱证据

若某候选仅由单条弱证据支撑：

- 不进入最终候选输出

### 7.4 时间线与摘要矛盾

若时间线和摘要相互矛盾：

- 优先保留原始证据
- 不做强归类

## 8. 测试策略

### 8.1 信号提取测试

覆盖：

- 从日志摘要和 timeline 中提取稳定信号
- 未命中模式时不产生伪信号

### 8.2 候选映射测试

覆盖：

- 信号组合稳定映射到预定义候选类型
- 证据不足时返回空候选

### 8.3 输出约束测试

覆盖：

- 最多 2 个候选
- 一定附带 supporting evidence
- 不出现“已确认根因”表述
- 不出现候选类型集合之外的新类型

2. 再生成 timeline
3. 最后把摘要和 timeline 输入候选根因模块

## 10. 成功标准

首版完成后，应满足以下标准：

- 能从当前证据中提取稳定信号
- 能生成 1 到 2 个候选根因
- 每个候选都附支持证据
- 不依赖历史 case 或规则库
- 不把候选写成最终根因
