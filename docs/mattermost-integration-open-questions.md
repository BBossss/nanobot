# Mattermost 接入待确认项（V1）

## 1. 目的

本清单用于在正式编写 `Mattermost` 接入设计前，确认内网 Mattermost 环境的关键约束，避免在不了解实际环境能力的情况下提前写死实现方案。

本清单关注以下问题：

- 能用什么接入方式
- 网络与证书环境如何
- Bot 能获取哪些消息上下文
- 安全边界如何设置
- 回消息和回线程的能力如何

待本清单信息确认后，再补充正式的 `Mattermost` 接入设计文档。

## 2. 接入方式待确认

需要确认内网 Mattermost 当前允许或推荐的接入模式：

- 是否支持 Bot Token
- 是否支持 Personal Access Token
- 是否支持 OAuth App
- 是否支持 Incoming Webhook
- 是否支持 Outgoing Webhook
- 是否支持 WebSocket 事件订阅
- 是否支持 Slash Command

### 需要确认的问题

- 推荐的官方接入方式是什么
- 是否有企业内部统一规范（例如只允许 Bot Token）
- 是否允许第三方程序长期持有 token
- 是否允许通过 WebSocket 保持长连接

### 对实现的影响

- 若支持 WebSocket：可优先考虑事件驱动模式
- 若只支持 HTTP API：需考虑轮询或 webhook 模式
- 若只允许 Slash Command：交互模式会更受限，但权限边界更清晰

## 3. 网络与部署环境待确认

需要确认 `nanobot` 部署节点与 Mattermost 的网络可达性。

### 需要确认的问题

- `nanobot` 部署节点是否可直连 Mattermost 服务地址
- 是否需要使用 HTTP/HTTPS 代理
- 是否存在出口限制
- 是否允许长连接（如 WebSocket）
- 是否使用自签证书或企业内部 CA
- 若使用 HTTPS，自签证书是否需要显式信任

### 对实现的影响

- 若存在代理或自签证书，需要在 channel 层单独配置
- 若长连接不稳定，可能需要回退到轮询或命令式交互

## 4. Bot 身份与权限待确认

需要确认 Mattermost 中 Bot 的实际权限边界。

### 需要确认的问题

- Bot 是否可以被创建为独立账号
- Bot 是否可以加入指定公共频道
- Bot 是否可以加入私有频道
- Bot 是否可以接收 DM
- Bot 是否可以读取线程上下文
- Bot 是否可以查看历史消息
- Bot 是否可以上传文件
- Bot 是否可以在消息中使用 markdown / 代码块

### 对实现的影响

- 若无法读取线程上下文，会影响“线程级会话隔离”
- 若无法 DM，只能通过频道触发
- 若无法上传文件，报告只能以内联文本返回

## 5. 消息接收能力待确认

需要确认 Bot 在接收消息时，能够拿到哪些字段。

### 需要确认的问题

- 是否能获取发送者唯一 ID
- 是否能获取发送者用户名
- 是否能获取频道 ID
- 是否能获取频道名称
- 是否能获取消息 ID
- 是否能获取线程 root post ID
- 是否能区分频道消息、线程消息、DM
- 是否能识别 `@mention`

### 对实现的影响

- 用户 ID 会影响 `allowFrom` 设计
- 线程 root post ID 会影响 session key 设计
- 若无法可靠识别 mention，则只能采用频道级或 DM 级规则

## 6. 消息触发模式待确认

需要先明确希望排障助手如何在 Mattermost 中被触发。

### 可能模式

- 仅 DM 响应
- 仅在被 `@mention` 时响应
- 指定频道内全部消息都响应
- 仅通过 Slash Command 响应
- 仅在指定线程内响应

### 需要确认的问题

- 企业内部更偏好哪种交互方式
- 是否需要降低误触发概率
- 是否允许机器人在公共频道直接回应

### 建议优先级

在未确认前，建议优先假设：

- DM
- 被 `@mention` 的频道消息

因为这两种模式最容易控制误触发和权限边界。

## 7. 消息发送能力待确认

需要确认 Bot 在发送消息时支持的能力范围。

### 需要确认的问题

- 是否支持普通文本消息
- 是否支持 markdown
- 是否支持代码块
- 是否支持引用回复
- 是否支持线程回复
- 是否支持上传文件
- 是否支持长消息自动拆分

### 对实现的影响

- 若支持线程回复，建议将排障上下文与输出绑定在线程中
- 若不支持文件上传，报告返回应限制长度并优先摘要化

## 8. 会话建模待确认

Mattermost 接入需要尽早确认会话隔离维度。

### 候选方案

- DM 维度：`mattermost:{channel_id}`
- 频道维度：`mattermost:{channel_id}`
- 线程维度：`mattermost:{channel_id}:{root_post_id}`

### 需要确认的问题

- 线程是否是常见协作方式
- 一个频道里是否可能并行发起多个排障任务
- 是否希望一个线程对应一个排障会话

### 当前建议

若 Mattermost 支持线程且上下文可取到，优先使用“线程级会话隔离”。

## 9. 用户鉴权与权限控制待确认

需要确认哪些人可以触发排障助手。

### 需要确认的问题

- 是否只允许指定用户
- 是否只允许指定用户组
- 是否只允许特定频道使用
- 是否需要区分只读排障与高风险审批角色
- 是否需要记录操作者和审批者

### 对实现的影响

- `allowFrom` 应以用户 ID 为主，而不是仅用用户名
- 如存在多角色，需要在后续扩展审批模型

## 10. 审计与合规待确认

需要确认企业内部对审计的要求。

### 需要确认的问题

- 是否要求记录每次通过 Mattermost 发起的排障请求
- 是否要求记录执行人身份
- 是否要求记录请求原文
- 是否要求回写执行结果到固定审计位置
- 是否要求保留操作时间和结果摘要

### 对实现的影响

- 会影响日志落盘格式
- 会影响是否需要额外的审计通知通道

## 11. 失败处理与可用性待确认

需要确认内网环境下对异常场景的容忍度。

### 需要确认的问题

- Mattermost 暂时不可达时是否需要自动重连
- 是否需要断线重连机制
- 是否允许消息重复投递
- 是否需要去重
- 若消息发送失败，是否需要本地补偿记录

### 对实现的影响

- 决定 channel 层是否需要消息去重
- 决定是否需要断线恢复与状态缓存

## 12. V1 建议默认假设（待确认前）

在正式查看内网文档之前，建议先使用以下临时假设做设计占位：

- 使用 Bot Token 接入
- 支持 HTTPS API
- 支持被 `@mention` 后响应
- 支持 DM
- 支持线程回复
- 可获取用户 ID、频道 ID、消息 ID、线程 root post ID
- 可发送 markdown 文本

这些仅用于前期设计占位，不应直接作为最终实现依据。
