# HCIGuard 接下来 2 到 3 个迭代建议

## 文档目的

这份文档用于团队同步：

- 当前阶段哪些基础能力已经具备
- 为什么“基础已具备”不等于“排障能力已经做强”
- 接下来 2 到 3 个迭代里，应该优先推进哪些能力
- 哪些方向暂时不应抢占优先级

本文不是实现计划，也不是任务拆解文档。它的作用是帮助团队在后续设计和排期时保持一致判断。

## 当前判断

HCIGuard 当前已经明显超过“通用 agent 套一层 HCI 话术”的阶段，正在形成自己的排障产品骨架。

当前已经具备的基础包括：

- investigation-first 的排障主路径
- 只读优先、审批文件、统一审计这些安全边界
- target-aware execution
- 多目标配置、分组解析、确认门控与受控 fan-out
- inspection、case、report、audit 这些可沉淀产物
- timeline artifact 的稳定边界

这说明项目已经不缺“能力入口”，也不缺“产品叙事”。接下来更重要的问题是：

**如何把这些基础能力继续推成更强的排障能力，而不是只停留在能力拼图已经齐全。**

## 一个重要判断

V1.1 的 multi-target foundations 可以认为大体完成了，但这不代表“多目标排障已经足够强”。

目前更准确的描述应该是：

- 多目标基础设施已经具备
- 多目标排障已经可用
- 但它还没有完全成长为项目最有杀伤力的核心能力

原因很直接：

- 当前多目标能力更像“受控 fan-out + 聚合摘要”，还不是成熟的跨目标定位系统
- 当前 strongest path 仍然更接近单节点/单目标深排障
- timeline、candidate、report、case 虽然已经有基础，但跨目标证据关联还没有完全打通
- 长会话和多轮调查下的上下文信噪比，还没有被明确当作排障能力的一部分来治理

因此，接下来不建议再把主要精力放在“是否还缺某个入口能力”上，而应转向：

**把已有基础能力往更强的证据收敛能力、跨目标定位能力和长会话稳定排障能力推进。**

## 迭代优先级总览

建议接下来按下面三个迭代推进：

1. Iteration 1：做强多目标排障聚合能力
2. Iteration 2：打通跨目标 incident timeline 与 evidence correlation
3. Iteration 3：优化长会话上下文信噪比，并增强候选根因收敛

整体优先级原则：

- 优先做直接增强排障半径和定位能力的工作
- 次优先做提高长流程稳定性的工作
- 暂不优先做主要改善展示层、但对定位能力帮助有限的工作

## Iteration 1：多目标排障聚合增强

### 目标

把当前的多目标排障从“多个目标上执行同一检查”推进到“对多个目标的证据进行稳定对比和归纳”。

### 为什么先做这个

这是当前最直接提升排障能力的一步。

项目已经有多目标配置、解析、确认门和受控 fan-out，这意味着基础设施已经在位。接下来最值钱的，不是再补新的入口，而是把已有多目标执行结果变成更可判断的排障证据。

如果这一步不做，系统虽然已经能“查多个节点”，但它给出的结果仍然更像是多个单节点结果的并排堆放，而不是面向故障定位的跨目标调查输出。

### 本轮应重点推进的能力

- 按工具类型稳定区分 `shared findings`、`local findings`、`failed targets`
- 对多目标结果做更强的共性/差异归纳
- 让用户能一眼看出哪些节点表现一致，哪些节点异常独有
- 为后续 timeline 和 root cause candidate 提供统一的聚合证据结构

### 预期收益

- 多节点场景下的排障效率明显提升
- 相同工具调用的跨目标结果更容易直接用于判断
- 后续 timeline / candidate / report 不再需要从松散文本重新抽取结构

### 非目标

- 不在这一轮做跨目标时间线关联
- 不在这一轮做自动根因判断升级
- 不把这一轮扩成“完全通用的集群编排系统”

### 完成信号

- 多目标只读检查的输出不再只是简单拼接结果
- 多目标聚合输出可以稳定回答“哪些节点一致、哪些节点不同、哪些节点失败”
- 针对最常用的多目标工具，聚合结果具备可预测的结构

## Iteration 2：跨目标 Incident Timeline 与 Evidence Correlation

### 目标

把当前已经存在的 log timeline、timeline artifact 和多目标聚合基础，推进成可用于 incident 定位的跨目标时间线能力。

### 为什么排第二

这是从“能查多个节点”走向“能解释故障如何发生和扩散”的关键一步。

对于真实 HCI 场景，很多故障并不难发现，难的是回答这些问题：

- 哪个节点最早出现异常
- 异常是局部问题还是逐步扩散
- 恢复信号是什么时候出现的
- 不同节点的关键证据能否被放到同一时间窗里理解

你现在已经补了 `timeline_artifact` 的稳定边界，这说明这条线的基础契约已经建立。下一步最自然的推进，就是把 timeline 真正接到多目标 incident analysis 上。

### 本轮应重点推进的能力

- 多目标日志/状态证据按 incident window 对齐
- 构建最小可用的 cross-target timeline
- 在 report 或 troubleshooting output 中回答“先发生了什么、后发生了什么”
- 明确保留证据引用，而不只是输出时间顺序总结

### 预期收益

- 定位能力从“症状并列”提升到“事件演进解释”
- timeline artifact 从稳定格式上升为有实际定位价值的产物
- 后续 case、handoff、root cause review 的可复用价值明显提升

### 非目标

- 不在这一轮做复杂的自动根因评分系统
- 不追求一次做成完整的 AIOps 事件关联平台
- 不扩大成高自由度、低约束的通用 timeline 生成器

### 完成信号

- 系统能在多目标 incident 中输出有时间窗、有目标边界、有证据引用的 timeline
- timeline 能明确表达异常出现、扩散、恢复三个阶段中的至少两个
- report / troubleshooting output 开始能稳定回答“what happened first”

## Iteration 3：长会话上下文信噪比优化与候选根因收敛增强

### 目标

在长会话、多轮调查、多目标切换场景下，保证排障能力不会因为上下文累积而变钝，同时让候选根因收敛更依赖结构化证据而不是语言惯性。

### 为什么排第三

这一轮很重要，但它更偏“能力稳定性增强”，而不是前两轮那种直接扩大排障半径。

当前项目已经有 memory window、consolidation、workflow runtime context 等机制，说明上下文问题并没有失控。但随着多目标调查、timeline、candidate、case 继续变强，长上下文带来的信噪比问题会越来越明显。

如果不提前治理，后续会出现这些风险：

- 关键 target / evidence / timeline 信息被聊天噪声冲淡
- 已失效假设在后续轮次里继续污染判断
- 多节点场景下的上下文串台
- 候选根因越来越像“延续之前的说法”，而不是基于当前证据收敛

### 本轮应重点推进的能力

- 引入结构化 troubleshooting working set
- 优先保留 target / evidence / hypothesis / next_step，而不是原始消息堆积
- 让 memory consolidation 更偏事实摘要，而不是会话总结
- 增强 root cause candidate 的证据绑定和缺口表达

### 预期收益

- 长会话下的排障深度更稳定
- 多轮 follow-up 不容易跑偏
- 候选根因输出更克制，也更可信
- 后续 case/handoff 的上下文复用质量更高

### 非目标

- 不把这一轮做成“泛化记忆系统”工程
- 不优先优化 token 利用率本身
- 不为了压缩上下文而丢掉关键证据或时间线信息

### 完成信号

- 长会话中仍能稳定保持 target、证据、下一步动作的一致性
- 候选根因输出与当前轮证据绑定更紧
- 上下文压缩后，排障准确性没有明显回退

## 暂不优先的事项

以下方向不是不做，而是暂时不应抢占前面三个迭代的优先级：

- 重 UI 或重展示层建设
- 过早做通用化 workflow 编排框架
- 自动修复/自动 remediation 扩张
- 重型 Web 控制台
- 为了“更像产品”而做大量表层交互包装
- 与排障主路径关系不强的泛能力扩展

这些方向的共同问题是：

它们可能提升产品感、完整度或观感，但在当前阶段，对“让 HCIGuard 变成更强的 HCI 排障助手”帮助不如前三个迭代直接。

## 最后的建议

如果团队希望继续保持 HCIGuard 的辨识度，那么接下来的推进不应把重点放在“再加多少能力”，而应放在：

- 多目标证据怎样被更好地组织
- 故障演进怎样被更好地解释
- 长流程排障怎样保持稳定、克制、可信

换句话说，下一阶段最重要的不是让 HCIGuard “看起来更大”，而是让它在真实 incident 里“更像一把真正能用的兵器”。
