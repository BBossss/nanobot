# HCI 排障助手 V1 巡检与报告规范

## 1. 目标

本规范用于定义 HCI 排障助手 V1 的定时巡检与报告机制，确保系统能够在无需人工持续盯守的情况下，定期扫描日志和关键状态信息，识别异常并输出结构化报告。

本规范主要解决以下问题：

- 巡检任务扫描什么
- 巡检任务如何控制输入规模
- 什么情况下判定为异常
- 报告以什么格式输出
- 什么时候生成案例

## 2. 适用范围

本规范适用于以下场景：

- 定时日志扫描
- 定时状态检查
- 手动触发巡检
- 巡检结果自动生成日报/周报

V1 以“本机巡检”为主，不包含任意跨主机巡检。

## 3. 总体原则

### 3.1 先过滤，后分析

巡检任务不得直接把完整大日志送入模型，必须先通过规则进行预过滤，再将高价值片段交给模型分析。

### 3.2 固定目标，固定模板

V1 巡检对象必须预定义，不允许模型临时决定大范围扫描目标。

### 3.3 结果结构化

巡检结果必须按照固定模板输出，便于阅读、归档和复用。

### 3.4 异常与正常分流

- 无异常或低价值结果：只写摘要或简报
- 有异常且达到阈值：生成正式报告
- 有明确风险：生成案例并触发通知（如配置允许）

## 4. 巡检对象定义

V1 巡检对象建议配置化定义，按“目标”组织。

每个巡检目标应至少包含：

- `name`
- `type`
- `source`
- `window`
- `keywords`
- `severity_rule`

### 4.1 支持的目标类型

V1 建议支持以下类型：

- `log_file`
  扫描指定日志文件

- `journal`
  扫描系统日志（如 `journalctl`）

- `command_check`
  执行预定义只读状态检查

### 4.2 示例

```json
{
  "name": "system-log",
  "type": "log_file",
  "source": "/var/log/messages",
  "window": "30m",
  "keywords": ["error", "failed", "critical"],
  "severity_rule": "keyword_count"
}
```

## 5. 巡检执行流程

### 5.1 标准流程

每次巡检按以下顺序执行：

1. 读取巡检目标配置
2. 按时间窗口收集原始输入
3. 使用规则做预过滤
4. 截断并整理高价值片段
5. 调用模型分析
6. 生成结构化报告
7. 根据规则决定是否生成案例
8. 根据配置决定是否通知用户

### 5.2 说明

V1 必须避免以下行为：

- 对单个大日志文件做无限制全量扫描
- 将大量无意义正常日志直接发给模型
- 用模型替代规则过滤

## 6. 输入控制策略

### 6.1 时间窗口限制

所有巡检任务必须定义时间窗口。

推荐窗口：

- `5m`
- `30m`
- `1h`
- `24h`

默认禁止无限窗口。

### 6.2 行数限制

巡检任务必须限制最大读取行数。

建议默认值：

- 单目标最大读取 2000 行
- 单次送入模型前最大保留 300 行高价值片段

### 6.3 匹配条数限制

关键字或错误码匹配结果必须限制条数。

建议默认值：

- 每个关键词最大保留 50 条
- 合并后总匹配结果不超过 100 条

### 6.4 输出大小限制

进入模型的文本总量应受限，避免过长上下文。

建议：

- 单目标分析片段不超过 64 KB 文本

## 7. 预过滤规则

V1 建议采用“规则优先”的预过滤方式。

### 7.1 关键字过滤

最基础的巡检方式：

- 匹配 `error`
- 匹配 `failed`
- 匹配 `critical`
- 匹配业务侧自定义错误关键词

### 7.2 错误码过滤

如现场有已知错误码，可优先按错误码匹配。

### 7.3 去重与聚合

对于重复日志，建议先做简单聚合，例如：

- 同一错误模板只保留前 N 条
- 统计重复次数

### 7.4 噪音排除

支持配置已知无害关键词或误报模式，避免无意义报警。

## 8. 异常判定规则

V1 建议将巡检结果分为 3 类：

- `normal`
  未发现异常，或仅有低价值噪音

- `warning`
  发现需要关注的问题，但未到高风险级别

- `critical`
  发现高风险异常，需尽快跟进

### 8.1 判定依据

可综合以下维度：

- 错误关键词出现次数
- 错误码类型
- 是否涉及关键服务
- 是否与历史高风险案例相似
- 模型判断出的风险等级

### 8.2 V1 建议规则

先使用简单规则初判，再由模型补充语义判断：

- 无匹配：`normal`
- 有少量异常匹配：`warning`
- 高频异常、关键错误码、关键组件异常：`critical`

## 9. 报告生成规则

### 9.1 报告生成时机

在以下场景生成巡检报告：

- 定时巡检任务结束后
- 用户手动触发巡检后

### 9.2 报告等级

V1 建议分两类报告：

- 简报
  用于无明显异常或低风险结果

- 正式报告
  用于发现异常并需要存档或通知的结果

### 9.3 报告存储位置

建议统一存放于：

- `reports/`

### 9.4 报告命名规则

建议：

- 日报：`daily-YYYY-MM-DD.md`
- 周报：`weekly-YYYY-WW.md`
- 手动巡检：`inspection-YYYYMMDD-HHMMSS.md`

## 10. 报告格式规范

### 10.1 报告最小结构

每份报告至少包含：

- 时间范围
- 巡检对象
- 扫描结果摘要
- 异常清单
- 关键证据摘要
- 风险等级
- 建议动作

### 10.2 推荐模板

```md
# 巡检报告

## 时间范围

- 开始时间：
- 结束时间：

## 巡检对象

- system-log
- cluster-status

## 扫描结果摘要

- 共扫描 2 个目标
- 发现 1 个 warning
- 未发现 critical

## 异常清单

### system-log

- 等级：warning
- 现象：最近 30 分钟出现多条磁盘相关错误日志
- 次数：12

## 关键证据摘要

- 摘要后的关键日志片段
- 异常指标简述

## 风险等级

- warning

## 建议动作

- 建议继续检查底层存储状态
- 建议关注未来 1 小时是否继续出现类似错误
```

## 11. 与案例沉淀的关系

巡检结果并不总是生成案例。

### 11.1 仅生成报告的情况

以下情况通常只生成报告，不单独生成案例：

- 无异常
- 低价值噪音
- 与已有未关闭案例重复且无新增信息

### 11.2 同时生成案例的情况

以下情况建议生成案例：

- 发现新的 `critical`
- 持续重复出现的 `warning`
- 命中关键错误码
- 与历史高风险案例相似
- 明确需要人工跟进

### 11.3 案例关联

若由巡检生成案例，建议在案例中记录：

- `trigger: scheduled`
- 所属巡检报告文件名或引用

同时在报告中记录：

- 生成的案例 ID

## 12. 通知规则

V1 可选支持通知，但不要求复杂告警编排。

### 12.1 可通知场景

- 新发现 `critical`
- 新生成案例
- 连续多次巡检发现相同异常

### 12.2 通知渠道

V1 可优先支持：

- CLI 输出
- Mattermost 消息

### 12.3 通知内容

通知应为摘要形式，包含：

- 风险等级
- 简要现象
- 报告位置
- 案例 ID（如已生成）

## 13. 配置建议

### 13.1 巡检配置结构

建议新增独立配置域：

```json
{
  "inspection": {
    "enabled": true,
    "reportDir": "~/.nanobot/workspace/reports",
    "defaultWindow": "30m",
    "targets": [
      {
        "name": "system-log",
        "type": "log_file",
        "source": "/var/log/messages",
        "window": "30m",
        "keywords": ["error", "failed", "critical"],
        "generateCaseOn": ["critical"]
      }
    ]
  }
}
```

### 13.2 任务调度建议

巡检可通过现有 `cron` 能力触发，例如：

- 每 30 分钟执行一次基础巡检
- 每天生成一次日报
- 每周生成一次周报

## 14. 失败处理策略

### 14.1 巡检失败

若巡检执行失败，应：

- 记录失败原因
- 在报告中注明部分目标未完成
- 保留审计记录

### 14.2 输入不足

若日志不足或无数据，应：

- 输出“数据不足”而非强行下结论
- 不生成误导性案例

### 14.3 模型分析失败

若模型调用失败，应：

- 保留规则过滤后的基础结果
- 输出简化版巡检摘要
- 不阻断整个巡检任务

## 15. 审计要求

每次巡检应记录：

- 巡检任务 ID
- 触发方式（定时 / 手动）
- 扫描目标
- 时间窗口
- 命中摘要
- 是否调用模型
- 是否生成报告
- 是否生成案例

建议审计信息写入：

- `audit/`
