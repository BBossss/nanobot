# HCI 排障助手 V1 PRD

## 1. 背景

当前深信服超融合 HCI 场景下的故障排查工作，主要依赖运维或现场支持工程师手工查看日志、执行只读诊断命令、比对历史案例并输出排查结论。该流程存在以下问题：

- 排查路径依赖个人经验，稳定性差
- 同类问题重复排查，历史经验难复用
- 日志量大，人工筛查耗时高
- 缺少统一的巡检与报告机制
- 即时协作多发生在 IM 中，排查入口分散

`nanobot` 已具备多模型、工具调用、记忆、定时任务、CLI 和 IM 渠道接入等基础能力，适合作为排障助手的二次开发底座。

## 2. 产品目标

基于 `nanobot` 构建一个面向深信服超融合 HCI 场景的智能排障助手，支持：

- 在本机执行受控的只读诊断
- 读取和分析日志，辅助定位问题
- 沉淀历史排查记录与经验
- 定时巡检日志并输出周期报告
- 通过 CLI 或 Mattermost 发起排障指令

V1 的目标不是“自动修复系统”，而是“提高定位效率、沉淀经验、降低重复劳动”。

## 3. 目标用户

- 一线运维工程师
- 售后实施工程师
- 现场支持工程师
- 内部技术支持团队

## 4. 核心价值

- 将重复性的日志筛查和信息汇总自动化
- 将经验型排障流程固化为标准化工作流
- 让历史案例可搜索、可复用
- 在不放开高危权限的前提下提供可控的智能辅助

## 5. 核心使用场景

### 场景 A：人工发起单机排障

用户在 CLI 或 Mattermost 中输入排障指令，例如：

- “检查当前节点最近 30 分钟是否有磁盘相关错误”
- “分析最近的集群告警并给出可能原因”

系统执行受控的只读检查，汇总日志和状态信息，输出：

- 已发现现象
- 初步判断
- 证据来源
- 建议下一步

### 场景 B：定时日志巡检

系统按预设计划扫描指定日志目录或固定只读命令输出，识别错误、告警、异常趋势，自动生成巡检报告。

### 场景 C：历史案例复用

用户询问类似历史问题，例如：

- “之前有没有类似的存储报错？”
- “这类网络异常之前是怎么处理的？”

系统从记忆和排查记录中提取相似案例并提供参考结论。

### 场景 D：IM 协作排查

用户在 Mattermost 中触发排障任务，系统返回分析结果、报告摘要和建议动作。

## 6. V1 范围

### V1 必做

- 基于 `nanobot` 的本机只读排障能力
- 多模型提供商支持（沿用 `nanobot` 现有能力）
- 记忆与排查记录沉淀
- 定时日志巡检
- 自动生成文本报告
- CLI 入口
- Mattermost 指令入口
- 命令白名单与高危操作拦截

### V1 可选

- 轻量可视化界面（只读报告查看页）

### V1 不做

- 任意跨主机 shell 执行
- 自动修复、自动重启、自动变更系统配置
- 高风险写操作
- 完整运维平台级 Web 控制台

## 7. 非目标

以下能力不属于 V1：

- 替代现有监控平台
- 替代工单系统
- 替代 CMDB
- 提供无边界的远程控制能力
- 对生产环境执行自动变更

## 8. 功能需求

### 8.1 本机排障

系统应支持在本机执行受控的只读诊断，包括但不限于：

- 查看指定日志文件最近 N 行
- 在日志中搜索错误关键字或错误码
- 读取系统状态信息（如进程、磁盘、内存、网络基础状态）
- 根据故障类型执行预定义的诊断组合

输出结果必须包含：

- 结论摘要
- 关键证据
- 风险等级
- 建议下一步

### 8.2 多模型支持

系统应支持多个模型提供商，优先复用 `nanobot` 已支持的：

- OpenAI Codex（OAuth）
- OpenRouter
- Anthropic
- 其他已集成提供商

系统应允许通过配置切换默认模型。

### 8.3 记忆与笔记

系统应保留：

- 长期事实（环境信息、常见问题、关键约束）
- 排查历史（带时间戳）
- 案例笔记（问题现象、根因、处置方式）

系统应支持根据历史案例提供相似问题参考。

### 8.3.1 排障记录沉淀机制

系统必须具备明确的排障记录沉淀机制，用于将每次排障过程转化为可复用的结构化经验。

每次排障任务完成后，系统应自动生成一份结构化摘要，至少包含：

- 时间
- 触发来源（CLI / Mattermost / 定时任务）
- 排障对象（主机、节点、服务或日志源）
- 问题现象
- 已执行检查项
- 关键证据摘要（日志片段、命令结果摘要）
- 初步结论
- 根因（如已确认）
- 建议下一步
- 是否已解决
- 是否需要人工跟进
- 标签（如存储、网络、虚拟化、告警）

### 8.3.2 存储分层

排障相关信息应分层存储，避免将所有内容混杂在单一记忆文件中：

- `memory/MEMORY.md`
  用于保存长期稳定事实，例如环境特征、关键约束、固定规则、用户偏好

- `memory/HISTORY.md`
  用于保存按时间追加的历史摘要，便于快速 grep 检索

- `notes/cases/`（或等价目录）
  用于保存每次排障的详细案例记录，作为后续复盘和相似问题检索的主要数据来源

V1 应以“案例文件 + 历史摘要”的方式沉淀排障记录，而不是仅依赖通用记忆文件。

### 8.3.3 写入时机

系统应在以下时机写入排障记录：

- 手动排障任务完成后自动写入
- 定时巡检发现异常并生成报告后写入
- 用户明确要求“记录本次排障”时，补写或强化记录

### 8.3.4 复用机制

系统应支持基于历史记录进行案例复用：

- 先按关键词、错误码、主机名、标签检索历史摘要和案例索引
- 再将相似案例摘要注入当前分析上下文
- 输出结果中应明确标注“参考自历史案例”与“当前已确认事实”的区别

### 8.3.5 现有案例库导入

系统应支持导入已有的排障案例库，以便在初始阶段快速建立可检索、可复用的经验基础。

导入目标可包括：

- 历史排障文档
- 运维手册中的故障案例章节
- FAQ / 知识库条目
- 既有巡检报告中的典型异常案例

V1 对导入能力的要求如下：

- 支持批量导入已有案例
- 支持为导入案例补充基础元数据
- 导入后可参与检索、匹配与案例复用
- 保留“导入来源”字段，区分历史导入案例与运行期新生成案例

V1 可优先支持以下输入形式：

- Markdown 文档
- 文本文件
- 结构化 JSON（可选）

对于导入案例，系统应尽量抽取以下字段：

- 标题
- 问题现象
- 适用环境
- 根因
- 处理方式
- 标签
- 来源

若原始文档不完全结构化，系统可在导入阶段进行摘要、归类和字段补全，但应保留原始内容引用。

### 8.4 规划能力

系统应支持多步排障流程，例如：

1. 收集上下文
2. 抽取日志片段
3. 执行只读检查
4. 汇总证据
5. 输出判断与建议

排障过程不应长时间静默，至少应提供以下可见反馈：

- 固定阶段进度（如“收集上下文”“执行只读检查”“汇总证据”）
- 关键调查动作前的简短原因说明
- 长耗时只读动作期间的等待提示
- 最终结论前的简短过程摘要

若处于多节点只读调查场景，应在用户确认范围后补充简短进度提示。

模型给出的结论必须区分：

- 已证实
- 高概率推断
- 需要人工确认

### 8.5 定时巡检

系统应支持定时任务，能够：

- 定时扫描指定日志
- 定时执行预定义只读检查
- 识别异常关键词、错误码、异常趋势
- 自动生成日报/周报

### 8.6 安全控制

系统必须默认采用最小权限原则：

- 默认只允许白名单中的只读命令
- 禁止高风险命令
- 非白名单命令需人工审批

白名单范围示例：

- `cat`
- `tail`
- `grep`
- `awk`（仅限受控模板）
- `sed`（仅限只读查看）
- `journalctl`
- `ps`
- `df`
- `free`
- `uptime`

默认禁止示例：

- `rm`
- `mv`
- `cp`
- `chmod`
- `chown`
- `systemctl restart`
- `reboot`
- `shutdown`
- 任意重定向写文件

### 8.7 CLI

系统应支持通过 CLI：

- 手动发起排障
- 查看历史报告
- 查询记忆/案例
- 手动触发定时任务

### 8.8 Mattermost 接入

系统应支持通过 Mattermost：

- 接收排障指令
- 反馈排查结果
- 返回报告摘要
- 以频道或线程为会话维度保留上下文

## 9. 跨主机策略

跨主机能力是中长期方向，但不作为 V1 的默认能力。

V1 原则：

- 不开放任意 SSH 执行
- 不允许模型自由拼接远程命令
- 先聚焦本机排障能力

V1.5 或后续版本可引入“受控远程采集”：

- 基于固定主机清单
- 基于固定只读采集模板
- 不直接暴露远程 shell

## 10. 部署形态与运行约束

### 10.1 V1 推荐部署形态

V1 推荐采用单实例部署，部署在一台受控的管理节点或运维侧虚机上。

推荐原则：

- 先以单机排障为主
- 不要求每个 HCI 节点都部署 agent
- 不默认提供分布式多节点部署能力
- 通过单个后台服务承载 CLI、定时巡检和 IM 网关能力

补充边界：

- 允许在用户明确确认后，对受限的一组只读调查动作执行多节点排查
- 该能力属于“受限范围扩查”，不等同于通用分布式编排平台

### 10.2 支持的安装方式

V1 支持以下安装方式：

- 源码安装（适合开发和调试）
- Python 虚拟环境安装（推荐）
- Docker 容器部署（可选）

V1 不要求提供复杂的集群化部署方案。

### 10.3 运行方式

系统应支持以下运行模式：

- CLI 手动执行排障任务
- 后台常驻运行（用于 IM 网关与定时巡检）
- 守护进程方式运行（如 system service、守护进程管理器）

V1 应默认支持单进程常驻运行，以简化部署和运维。

### 10.4 环境约束

部署环境应满足以下基本条件：

- 具备 Python 3.11+ 运行环境
- 可访问目标日志目录或只读诊断数据源
- 可访问模型提供商网络出口（如 OpenRouter / OpenAI）
- 如接入 Mattermost，需要具备到 Mattermost 服务的网络连通性

### 10.5 权限要求

系统部署必须遵循最小权限原则：

- 不建议以 `root` 身份直接运行
- 推荐使用专用受限账号运行
- 通过组权限、目录授权或受控命令方式访问日志与系统信息
- 不因部署在管理节点就默认放开高危命令

### 10.6 V1 非目标

以下不属于 V1 的部署目标：

- 多节点高可用部署
- 分布式任务调度集群
- 每台主机安装独立 agent
- 自动化跨主机编排执行框架

但以下能力可以作为 V1 范围内的受限增强：

- 用户确认后的多节点只读扩查
- 多节点调查过程中的简短进度反馈与结果汇总

## 11. 安全与审计要求

- 所有执行过的诊断命令都应可审计
- 所有模型生成的结论应保留执行上下文
- 高风险操作必须显式拦截
- 输出内容应支持后续脱敏扩展
- IM 入口必须支持用户身份限制

## 12. 输出物要求

### 排障结果

每次排障至少输出以下结构：

- 问题摘要
- 已检查项
- 关键日志/证据
- 初步结论
- 风险等级
- 建议下一步

### 巡检报告

每次巡检报告至少包含：

- 时间范围
- 扫描对象
- 异常摘要
- 新发现问题
- 历史已知问题对比
- 建议关注项

### 案例记录

每次排障案例记录至少包含：

- 基本信息（时间、来源、对象）
- 问题描述
- 检查过程摘要
- 关键证据
- 结论与判断
- 后续建议
- 标签与分类

## 13. 技术方案概览

基于 `nanobot` 的能力进行二次开发：

- 保留 `AgentLoop` 作为调度核心
- 新增只读命令网关，替代直接自由执行
- 新增 HCI 排障 Skill，固化排障工作流
- 使用 `memory` 能力沉淀长期信息和历史记录
- 使用 `cron` 和 `heartbeat` 实现定时巡检
- 新增 Mattermost Channel
- 可选增加轻量 Web 报告查看页

## 14. 成功指标

V1 验收可参考以下指标：

- 支持至少 10 类常见日志异常的识别
- 单次基础排障在 2 分钟内输出结构化结论
- 定时巡检能稳定生成日报
- 所有执行命令可追踪
- 默认情况下不允许执行高危命令
- 用户可通过 CLI 和 Mattermost 触发排障

## 15. 主要风险

- 模型对日志结论存在误判风险
- 日志量大时上下文成本过高
- 若安全边界设计不严，可能带来运维风险
- Mattermost 接入与会话建模不当，可能导致上下文串线
- 跨主机需求若提前引入，可能拖慢整体交付

## 16. 里程碑建议

### M1：单机只读排障

- 命令白名单
- 本机日志分析
- 结构化排障输出

### M2：记忆与巡检

- 案例沉淀
- 现有案例库导入
- 定时日志扫描
- 自动报告输出

### M3：协作入口

- Mattermost 接入
- IM 会话隔离

### M4：增强能力

- 轻量可视化界面
- 受控跨主机采集
